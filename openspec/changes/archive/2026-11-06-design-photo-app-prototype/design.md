# Design

## Context

项目名为 encrypted-photo-app，目标是用户个人在 Windows 与 iPhone 之间管理和同步照片。问题与范围见 [proposal.md](proposal.md)。当前仍是规划与原型阶段，没有 Flutter 工程、真实账号连接、加密实现或同步服务。

本文件依据 2026-11-06 的用户确认更新。此前草案中没有得到确认的技术选择和默认行为已移出必做方案。文档完整表示需求已记录，不表示 Open Questions 中的实现决策已经完成。

## Goals / Non-Goals

**Goals:**

- 记录用户已经决定的平台、存储、密码、应用锁、验证周期和删除语义。
- 让提案、功能规格、任务清单与项目配置保持一致。
- 后续先用明确标识的交互原型验证使用流程，再单独确定真实加密、授权、同步和原图删除的实现。
- 优先考虑数据安全、稳定性和长期可维护性。

**Non-Goals:**

- 本次不创建应用代码、不进行账号授权、不访问或修改真实照片和远端仓库。
- 不自行确定加密算法、密码派生参数、内部密钥保存机制或具体 Flutter 插件。
- 不接入 iCloud，不在产品界面加入 iCloud 相关说明。
- 不把支持两种仓库平台自动解释成同时向两边镜像、自动创建多个仓库或无限容量保证。

## Decisions

### 1. 已确认的产品决定

| 编号 | 已确认内容 | 对应规格 |
| --- | --- | --- |
| D01 | 主要供用户个人使用，Windows 和 iPhone 都是正式使用端；需要浏览、整理、导入和导出照片 | photo-library |
| D02 | 客户端采用 Flutter + Dart，目标为 Windows 桌面应用和 iOS 应用 | 本设计及 tasks.md |
| D03 | 支持 GitHub、Gitee 授权登录及私有仓库选择 | repository-connection |
| D04 | Windows 原照片集中在普通源目录中，保留普通图片；上传之前必须完成客户端加密 | photo-library、encrypted-storage |
| D05 | 密文需要分块，尽量控制在每块 50 MB 以内；应用不人为设置照片库总容量配额 | encrypted-storage |
| D06 | 用户设置并记住照片解密密码，App 提醒用户记忆；不要求用户手动设置或保管解密密钥 | vault-onboarding |
| D07 | 两端均设置四位数字应用锁，普通上锁后只显示密码输入界面 | app-access-control |
| D08 | 从上次正确输入照片解密密码开始，每 3 天强制验证；未通过时不能查看照片，且暂停同步；正确验证后重新计时并恢复 | app-access-control、backup-management |
| D09 | 提供删除本地保留仓库、同步删除、删除仓库保留本地三种选择；本地指 Windows 原目录或 iPhone 系统相册原照片 | photo-library |
| D10 | 产品按不使用 iCloud 的前提设计，不加入相关界面说明 | 本设计及项目配置 |
| D11 | 应用需要自动进行文件同步，平台授权与四位应用锁不能代替照片解密密码验证 | backup-management、repository-connection、device-recovery |

### 2. 客户端与平台边界

Flutter + Dart 是已确定的客户端技术路线。状态管理、路由、数据库、加密库、授权库及原生插件仍未选择。

Windows 原目录保持明文，因此应用锁保护 App 内访问，不把普通源目录变成加密磁盘。iPhone 的本地原照片来自系统相册。两端要对接各自的文件、照片权限和系统能力；原型阶段以明确标识的模拟交互表达，不把模拟授权和删除当作实际系统操作。

当前不沿用旧草案的网页优先实施路线、固定四个底部标签、具体配色或额外设备管理流程。这些界面细节需要在后续原型工作中再讨论。

### 3. 三种凭据的职责

| 凭据 | 已确认用途 | 尚未确定的实现 |
| --- | --- | --- |
| GitHub/Gitee 平台授权 | 连接对应平台和所选私有仓库 | 具体授权流程、权限范围、令牌存储与刷新 |
| 照片解密密码 | 用户记忆并输入，解锁照片库以及每 3 天强制复验 | 密码强度、派生算法、内部密钥保存、遗忘及更换处理 |
| 四位数字应用锁 | 限制当前客户端界面访问 | 两端设置是否同步、触发时机、失败重试、重置流程 |

“不要求用户设置解密密钥”是交互要求，不表示密码学内部没有密钥。不能把四位应用锁密码用作照片解密密码，也不能把平台登录成功视为照片密码已验证。

用户需要看到记住照片解密密码的明确提示。现阶段未确认恢复码、密钥文件保管或已有设备批准等额外解锁方式。

### 4. 应用锁与三天验证的组合

| 状态或事件 | 照片访问 | 同步 | 周期变化 |
| --- | --- | --- | --- |
| 普通应用锁上锁，照片密码周期未到期 | 仅密码输入界面 | 普通上锁是否暂停同步尚待确认 | 不因普通上锁改变 |
| 周期未到期，四位密码正确且照片库已解锁 | 可访问 | 仍遵守其他运行条件 | 不重置照片密码周期 |
| 照片密码验证周期到期 | 必须正确输入照片解密密码后才能访问 | 暂停 | 等待正确输入 |
| 到期后四位密码正确或平台重新授权成功 | 仍被到期验证阻断 | 继续暂停 | 不重置 |
| 到期后照片解密密码错误 | 继续阻断 | 继续暂停 | 不重置 |
| 照片解密密码正确 | 解除到期阻断，普通应用锁条件仍须满足 | 解除此次到期造成的暂停，接续未完成任务 | 从此次成功输入开始新的 3 天周期 |

原型可以使用可控的模拟时间检查上述规则，但模拟时间机制不是正式计时方案。跨端是否共享周期、重启与离线状态如何保留、系统时间改变如何处理及在途请求如何暂停，见 Open Questions。

### 5. 存储与同步的已确认边界

数据路径为：本地原照片由客户端处理，在上传前加密，密文按块同步至所选私有仓库，使用时在客户端解密。

“所有照片放在一个文件夹”记录为用户的照片源组织方式；这并没有决定内部密文必须是一个整库压缩包或仓库内必须使用单层目录。逐照片分块、批量打包、清单格式和实际目录布局均待选型。

50 MB 是用户提出的分块目标。单位、认证开销、默认块大小、例外和超限处理尚未约定，不在本次擅自换算成固定字节值。应用不设自有总容量配额，但需要处理平台容量、大小、权限和请求限制；具体策略待定。

为保持模块可维护性，可以后续评估照片管理、访问控制、加密和平台存储的职责边界。本次不把候选模块实现、协议、目录格式或库写成已经批准的架构。

### 6. 删除语义

| 用户选择 | 原照片处理 | 仓库副本处理 |
| --- | --- | --- |
| 删除本地，保留仓库副本 | 删除当前设备的 Windows 原目录或 iPhone 系统相册原照片 | 保留 |
| 同步删除 | 将原照片删除操作同步给参与该照片库的客户端 | 删除 |
| 删除仓库副本，保留本地 | 保留原照片 | 删除 |

这里的本地删除不等于清理 App 缓存。只有相应原照片实际删除成功，才能报告该原照片删除完成。

以下建议还没有被用户确认：删除本地前必须校验仓库副本可恢复、自动避免再次下载或上传的具体规则、回收站或保留期限，以及彻底清理仓库历史。因此不能把这些作为已选定的删除前置条件或保证。有关冲突与外部删除的处理见 Open Questions。

### 7. 本阶段的原型边界

当前变更继续服务于产品规划与交互原型。七份规格记录目标产品的行为契约；tasks.md 只安排下一阶段的 Flutter 原型任务，不把真实授权、真实加密、真实上传和真实删除混入模拟验收。

原型可以用虚构账号、仓库、照片、密码和任务演示已确认流程，必须表明模拟性质。任何真实密码学、仓库连接或原图删除实施都需要先完成相应设计和验证，不能因为原型页面可点击就认为已经具备生产能力。

## Risks / Trade-offs

- [四位应用锁被误当作照片解密能力] → 在文档与原型中区分两种密码，验证四位密码和平台授权均不能绕过三天到期验证。
- [要求无限制增长被理解为平台无上限] → 保留应用不设配额的要求，同时将外部限制处理列为待决事项。
- [模拟删除被理解成真实原图已删] → 明确演示性质；正式实现要分别验证 Windows 原文件和 iPhone 原照片的操作结果。
- [文档齐全被理解为可以直接选择算法实施] → 下列 Open Questions 对相关真实功能构成实现前置决策，不能用默认猜测补齐。
- [旧草案的恢复码、默认网络策略被当作用户决定] → 本次移除这些必做项，后续只有重新明确需求才纳入范围。
