## Goals / Non-Goals

**Goals:**

- 让同一套 Flutter 业务规则服务于两端的媒体、相册、选择、隐藏和上传交互。
- 把已确认的系统相册事件处理成可持久化、可重复核对的状态转换；名称变化明确产生新关联。
- 以真实文件、密码学、平台接口、加密持久化和真实音视频验证完整链路；测试替身限于隔离测试，不进入正式运行入口。
- 保持照片、媒体原文件删除、相册成员调整与来源跟踪删除的职责清晰。

**Non-Goals:**

- 不擅自决定安全、授权、仓库及删除未决方案；这些基础能力的设计评审和实施已纳入本变更，不再将它们整体排除。新增托管服务／恢复码等仍需独立授权。
- 不增加短视频平台下载、分享、图片／视频编辑、专业视频调色或强制转码功能。
- 不增加远端原文件全量下载。用户在本次澄清：移动端默认“全部同步”是将 iPhone 本机照片库全部可访问媒体纳入 App。
- 不把尚未确认的相册元数据跨 Windows／iOS 仓库同步、系统智能分类导入或目录名自动映射相册加入本次验收范围。
- 不重做品牌、页面导航或构建发布流程；不承诺 App 终止后持续运行。

## Decisions

### Windows Data Location — 2026-11-09

用户追加首次密码设置时选择程序数据保存目的地。这是已授权的本机初始化行为扩展，沿用 TD01–TD07，不变更密码学、密钥层次、远端协议或删除策略。

- 界面复用已有 file_selector 1.1.0 的系统文件夹选择器。用户选择父目录后，显示完整的 EncryptedPhotoApp 专用子目录；可恢复默认。取消、切换选择和未提交退出不创建自定义文件；表单校验通过并提交后才落盘。
- 只允许可访问的本机磁盘路径；拒绝网络／映射网络位置及任意祖先中的重解析点。创建专用目录时沿用现有 Windows 用户／SYSTEM 私有 ACL，不能满足要求的文件系统明确失败，不修改所选父目录权限。不接受已有的自定义子目录，避免覆盖、收紧无关目录权限或把旧库当新库；已运行的默认库保持原逻辑。本次不提供迁移或已有库导入。
- 新增 lib/app/vault_location_store.dart，固定在原 LocalAppData/EncryptedPhotoApp 保存少量启动文件：data-location.sealed 为版本化目录定位记录，经现有 WindowsProtectedStore／DPAPI 保护；location.lock 对同一用户配置串行化启动与初始化。真正的 catalog.db、vault.bootstrap、PIN／期限／辅助材料写入所选位置，并保留该目录的 instance.lock。
- 选择只存在内存。提交时复查目标未被其他程序占用，创建私有目录、持有目标实例锁，先原子保存密封定位记录，再创建凭据及加密目录。记录之后中断时，新启动只能报告目标不完整，不能自动创建另一份空库；初次目录创建前失败不改写定位记录。没有自定义记录的旧库继续从默认目录打开。
- 已记录的目标不存在时先拒绝，不执行递归建目录；定位记录损坏／未知版本、权限异常、缺必要库文件同样拒绝。目录恢复到原位置后可重新按旧凭据打开。此项不提供丢失密钥恢复或绕过密码。
- VaultController 绑定实际目录并管理选址与实例锁；production_screens.dart 仅首次设置显示选址，锁屏仍只提供密码访问；main.dart 正常入口通过原 controller 构造方式读取定位。不得为了展示此功能清除或移动用户现有数据。
- 同日追加设置页展示：在正常已解锁的“访问与密码”页增加“程序的数据保存目的地”及可选中的完整路径，直接读取 VaultController.directory.absolute.path。默认和自定义目录共用此来源；不新增持久化记录或位置更改入口，锁定时随原页面撤销。复用生产表单集成测试核对真实自定义目录展示与锁定后隐藏。
- 验收分层：真实后端测试验证 DPAPI 定位、SQLCipher 建库、重新创建控制器后同库／同期限及 PIN、目标缺失／文件缺失／损坏／并发／路径占用；表单测试的原生选择结果是测试替身，必须另列真实 Windows 选择器与编译结果。完整系统锁屏／挂起和 App 中断矩阵仍在 2.5／2.6。

2026-11-09 用户体验后追加密码输入显隐切换。正常入口中的首次设置、照片密码／PIN 验证、PIN 重设及改密对话框复用独立有状态输入组件：默认遮蔽，每框独立，保留原输入限制及禁止输入法学习设置；显隐只在页面内存中，验证禁用输入时恢复隐藏，页面销毁即丢弃。不读取已存凭据，不改变密码学、锁定及重试规则。此项属于 2.5 的已授权界面改进，不解除该任务剩余平台验收门槛。

下列是职责边界和已确认行为的实施安排。TD01–TD06 已获 SFR-1 明确批准；technical-decisions.md 的其余待决项仍是显式前置门槛。acceptance.md 的 AC01–AC26 定义真实验收，不能将安全方案批准扩大为仓库协议或删除选型批准。

### D1. 共享领域模型与平台适配边界

继续使用 Flutter 及已有共享规则。正式根状态通过明确的业务服务边界连接加密目录、访问控制、平台来源和仓库执行器；现有 DemoStore 的模拟行为只可作为隔离测试历史参考，正式入口不得实例化或故障回退至它。现有选择／查询／相册逻辑在保持规则的前提下接入真实事务。首次未配置显示真实初始化流程，已配置重启遵守 PIN；无媒体显示空库。

| 模型 | 拟记录的信息 | 原因 |
| --- | --- | --- |
| 媒体项目 | 内部 ID、种类、拍摄时间、大小、收藏、来源引用、当前资源版本及副本状态 | 一个 Live Photo 是一个项目，原文件名不再承担项目身份 |
| 原始资源 | 所属媒体 ID、资源角色、来源位置或平台资源标识、原始文件名、读取结果 | 支持静态图与配对视频，保持原始内容和关联 |
| App 相册 | 内部 ID、显示名称、隐藏设置、成员关系 | 名称可改且可重复，不能作为主键 |
| 相册来源观察记录 | 本机来源 ID、上次实际观察的系统名称、观察状态 | 在停止跟踪后仍须识别后来的系统改名 |
| 相册导入关联 | 来源 ID、导入代次、App 相册 ID、跟踪状态、系统成员快照、App 加入／移出覆盖 | 区分旧相册、新导入相册及用户独立整理 |
| 上传请求 | 目标仓库、媒体 ID、资源版本、处理状态与结果 | 单项、批量和自动上传共用去重和阻断规则 |

同一来源媒体在多个相册出现只增加归属关系，不重复建立媒体项目。跨路径或跨设备的内容去重不直接用文件名推断，本变更不选定全局哈希／合并协议。

替代方案：继续给 `DemoPhoto` 添加大量条件字段会让样片状态成为真实存储协议；按相册复制媒体会增加重复文件与删除歧义。拟采用共享模型与平台适配边界，测试替身保持在隔离测试中，正式执行只连接真实服务。

### D2. 单一查询范围服务于显示、计数与选择

查询条件包含当前视图、相册 ID、搜索词和现有状态筛选。聚合视图在应用搜索／状态筛选前排除属于任意隐藏相册的媒体；相册内部查询保留其成员。相册设置不改变备份资格和收藏值。

列表数量、日期分组数量、对应侧栏计数、全选和查看来源使用同一查询结果。同步中心仍反映实际同步任务，不把“隐藏”扩展为全局隐身或停止备份。

拟定交互默认值：

- 全选在点击时取得当前完整结果的 ID 集合，不依赖已创建的网格卡片；稍后新导入的媒体不自动变成已选择项目。
- 切换相册、搜索或筛选时清空选择，避免用户对看不见的旧选择执行删除；数据变化导致项目被隐藏／删除时，从当前选择中剔除。
- 进入选择模式后点击卡片切换选中；普通浏览点击打开全屏查看；“查看详情”保留为信息入口。
- 现有相册的隐藏设置默认关闭，保持旧数据原有可见性。新相册也默认关闭，用户可显式开启；这是待审核的迁移默认值。

替代方案：让每个界面分别过滤会造成数量不一致；把全选实现为选择屏幕卡片会遗漏未显示结果。共享查询对象解决这两类问题。

### D3. 批量操作逐项执行并维护真实结果

批量命令在触发时冻结有效选中 ID，再逐项校验权限、来源和当前状态；一次选择范围不授权操作未选中的媒体。收藏与成员关系修改复用单项业务逻辑，删除复用三个既有范围。

用户取消不产生副作用；部分失败保留每项结果，重新执行时跳过已经完成的同一操作。对 Live Photo 使用一个逻辑操作聚合多个必要资源的结果，资源不完整时不能显示整个项目成功。删除相册／移出相册只处理分组关系，不调用媒体原文件删除命令。

“上传”菜单位于“查看详情”之后；选择工具栏复用同一上传请求入口。仓库删除后的显式上传只重新排队所选项目，不能解除其他项目的保留本地状态。

### D4. 取消标题并保留可识别的操作界面

取消导入时生成“新的回忆”等展示标题，移除卡片标题和文件名两处文本；保留大小、状态、收藏、菜单，并为视频提供类型／时长、为实况提供标识。

原文件名只在详情内容中展示。同步队列、删除／导出提示和最近活动中原先引用 `photo.title` 的位置，拟改用缩略图、时间、媒体类型与操作数量识别项目；不把内部 ID 重新包装成照片名字。原始文件名仍可作为搜索依据，也仍是实际导出资源的文件名，UI 隐藏不重命名原文件。

现有“点击卡片打开详情”变为全屏查看；菜单“查看详情”继续打开信息面板。图片缩放手势、快捷键、连续浏览手势等未逐项确认，不列为本轮强制新增功能。

### D5. iPhone 相册采用来源观察与导入代次分离

来源的本机标识用于识别同一个系统对象是否发生名称变化，但不能因此维持旧 App 关联。每次观察到来源名称变化都结束旧代次并建立新代次，符合用户“改名导入新相册”的要求。

| 当前状态／来源事件 | 设计处理 |
| --- | --- |
| 新发现的普通系统相册 | 创建 App 相册与活动关联，名称和初始成员取来源当前值 |
| 活动关联，来源名称不变、成员变化 | 仅应用成员差异，并尊重 App 内覆盖 |
| 活动关联，来源名称变化 | 冻结旧 App 相册当前名称及有效成员，结束旧关联；新建 App 相册并按来源当前成员建立新关联 |
| 系统相册确认删除 | 将旧关联结束，保留 App 相册的最后有效名称和成员；不先应用“全部成员移除” |
| App 删除相册 | 删除 App 分组，保留该代次的停止跟踪记录与来源名称观察记录 |
| 已停止关联，来源名称未变 | 忽略成员导入，不因补扫或重启恢复 App 相册 |
| 已停止关联，来源名称变化 | 自动创建新代次并导入新相册；停止记录只约束旧代次 |
| 用户手动“导入相册” | 选择可访问来源，按当前名称与成员建立／恢复活动导入，不回写系统 |
| 权限受限、读取失败或来源暂不可见 | 保留最后状态并报告未完成核对，不判定删除或改名 |

来源观察、停止记录和新相册建立应在一次本地事务中保存；处理中断后重复读取同一快照不重复生成新相册。旧 App 相册已经删除时，改名事件只创建新相册，不复活旧记录。

技术边界：不用名称单独识别来源，因此两个系统相册同名不合并。拟将观察到的 `A → B → A` 视为两个改名事件，各产生一个新导入代次；重复读取没有变化的 A 不产生新代次。同名展示可并存，ID 负责区分。App 不运行期间若名称改动后又改回，且系统未提供可恢复的中间变化，不能声称还原了未观察到的历史；启动时核对可见最终状态。这是观察能力的限制，不能伪造事件。

手动导入已经活动跟踪的来源，拟反馈“已导入”并保持原关联，避免普通重复点击制造副本；用户要求的系统改名事件仍始终产生新代次。

### D6. 系统成员差异与 App 调整分开保存

用户在本次明确选择“保留 App 内的调整，仅合并系统侧的新变化”。拟分别维护来源当前成员集合 S、App 显式加入集合 A、App 显式移出集合 R；有效成员为 **（S 与 A 的并集）减去 R**，一次 App 操作会清除同一成员的相反覆盖。

来源变化只更新 S，不能抹掉 A 或 R。App 增加来源中已有成员也可以表达显式保留意图；App 移出成员则保留排除意图。若以后用户在 App 再加入，后一次 App 操作覆盖前一次决定。

例如：来源成员原为甲、乙；用户在 App 移出甲、加入丙；来源随后移出乙、加入丁，则有效成员为丙、丁。之后来源重新加入甲，也不会覆盖 App 对甲的显式移出。

系统改名时，把旧相册当时的有效成员冻结为其普通成员；新相册从来源当前成员开始，不把旧相册独立整理结果偷偷移植到新相册。App 内改名只改显示名称，不改上次观察的系统名称，也不触发系统写入。

替代方案：每次用完整系统成员列表覆盖会丢失用户整理；只记录一个混合列表又无法区分本地意图和来源变更。分层集合可以直接验证已确认的冲突优先级。

### D7. 两端媒体导入复用来源和资源接口

Windows：选择目录后进行递归扫描，监测事件用于触发核对，启动补扫作为漏事件补偿。按稳定来源信息避免同一文件重复导入；大文件写入未完成时不能提交半份媒体。目录不可访问、循环链接或读取失败须产生准确扫描结果，不能当作用户删除备份。监测销毁、扫描取消和根目录边界与窗口／来源生命周期一致。

iOS：媒体扫描独立于相册扫描，先覆盖权限允许读取的本机照片、视频和 Live Photos，再建立普通相册归属；未分类媒体同样纳入管理。拟使用 PhotoKit 的资产资源与变化观察能力 [R1][R2]，以本机资源引用为入口，按需读取原始资源，不默认把整库再复制一遍到 App 沙盒。

相册读取与媒体读取分别报告权限结果。苹果文档说明有限照片访问下不能获取用户相册 [R3]；这时媒体导入只能覆盖获准资产，相册导入提示所需权限并保留旧状态，不能写入“空列表”覆盖。权限说明加入 iOS 平台配置，不把拒绝授权当作允许删除。

Live Photo 通过资源角色与平台关联数据识别，不能只按同名 JPG／MOV 猜配；Windows 来源如何可靠识别导出的实况配对，需使用真实样本验证。确认不了配对时保留资源、报告未识别状态，不冒充已完整导入 Live Photo。[R1]

### D8. 全屏查看与播放后端解耦

全屏查看器接收媒体 ID、受限来源视图与访问状态，照片使用图像呈现，视频／Live Photo 使用播放器适配接口。原始资源与封面分离；列表不自动加载所有原始视频。视频控制包括播放／暂停、进度和声音，Live Photo 列表只用静态封面及标识。

media_kit 已获准接入验证，当前接口可以继续验证；ProRes 人工样本失败，因此完整支持仍未完成。继续验证该后端与经批准补充原生适配的优缺点见 TD15；不能因依赖已加入就认定双端可用，不能擅自更换后端、强制转码或删减已确认格式。真实 iPhone H.264／HEVC／ProRes、平台保存视频及 Live Photo 样本须记录资源来源、编码、音轨及两端结果。

内存、解密暂存和原生播放器的随机访问需求应共同评估，不擅自生成上传用有损转码副本。完整播放器停止必须包含画面、音轨、资源读取和异步回调：在访问状态变化时先使播放会话失效并停止输出，再由现有根 Navigator 替换界面。解锁后重新校验访问条件，不让旧回调恢复声音。

### D9. 上传使用统一请求边界，正式安全能力保持前置依赖

自动、单项和批量入口都提交“当前目的仓库＋媒体 ID＋资源版本”的请求。已有相同请求复用；当前目的仓库中内容未变且已确认完整的副本跳过；原文件不可读或实况资源不完整时反馈真实状态。不能把前一个仓库的完成标志带到新的仓库。

执行顺序保持读取版本确认、客户端加密、密文分块、上传、确认完整结果。大视频采用有界内存和分段处理，Live Photo 的全部必要资源完成后才发布项目完成状态。若处理期间来源变化，不能将不同资源版本拼成“成功”结果。

三天验证过期阻断所有上传入口；验证成功只解除该原因，不解除用户手动暂停或其他故障。2026-11-11 用户批准 WBL-1：Windows 最小化／手动 PIN 锁只撤销界面，后台完整导入和同步继续；系统安全锁、退出及到期仍全撤销。密钥保留边界和旧查看回调撤销见 windows-background-lock.md。

当前缺失的基础能力由本变更主动实施，决策批准和实现验收是两个独立步骤：

| 依赖 | 本变更负责的任务 | 接入门槛 |
| --- | --- | --- |
| 密码学、密钥、锁与复验 | 阶段 1 | TD01–TD06 批准并通过相关实际验证 |
| 加密本机目录与生命周期 | 阶段 2 | TD07 正式接入批准、双端实际证据；隔离探针不等同 App 接入 |
| GitHub／Gitee 授权及私有仓库 API | 阶段 3 | 两个平台分别验证，令牌安全保存和权限处理真实可用 |
| 密文格式、分块、队列、下载恢复 | 阶段 4 | TD09–TD11 批准；无原图／缓存独立恢复，不能仅验证发送端状态 |
| 来源、播放及相册业务 | 阶段 5–6 | 真实系统来源、持久化结果及已确认格式双端证据 |
| 导出、删除与恢复 | 阶段 7 | TD12/TD14 批准并用隔离副本检查实际作用范围 |

接口／请求规划完成不解除上述门槛；缺能力时禁用对应执行并标记未实现。接口结构可复用，但不得让 UI 直接修改“已备份”或“已删除”布尔值冒充结果。

### D10. 持久化与同步数据的范围

2026-11-09 实施期间用户确认本机管理元数据也必须加密，普通 SQLite 明文方案未获接受。随后批准先验证 SQLCipher，确定三天内允许系统安全存储辅助解锁、重启仍需四位应用锁；辅助解锁不能重置周期，到期仍需正确照片密码。密码／密钥／门禁方案已按 SFR-1 批准，目录后端比较见 `local-metadata-design.md`，SQLCipher 历史验证见 `sqlcipher-validation.md`，新凭据模块的真实证据见 `credential-bootstrap-implementation.md`。目录持久化及启动补扫仍须完成双端验证与 TD07 正式接入批准，当前内存预览不代表这些任务完成。用户已批准 `media_kit` 候选接入验证，双端真实格式验收仍必须逐项完成。

需要持久化导入来源、媒体引用、相册 ID／成员／设置、系统观察名称、导入代次、停止状态、App 成员覆盖和任务状态。采用独立目录层接口，具体数据库或文件格式作为可替换后端审核，不能让 UI 直接序列化演示对象。

本地事务至少保证“结束旧关联＋创建新相册＋推进观察名称”一起提交；重启读取版本化结构，失败保留最后可恢复状态。真实凭据与解密材料不进入此普通元数据接口。

相册名称、成员和隐藏设置是否作为仓库中的跨客户端加密元数据，前文仅提出建议，用户尚未确认；本变更只定义本机来源到 App 的关系，仓库元数据协议另行确定，不上传明文相册清单作为临时替代方案。

| 跨启动核对 | 已停止关联不复活；已处理改名不重复创建；App 成员覆盖仍有效 |

## Risks / Trade-offs

- [ProRes／HEVC 在某个目标端无法正确播放] → 在真实编码样本上先验证画面、声音、定位、方向与颜色表现，记录系统及设备；未通过则相关功能未完成，不能仅用封面或模拟器运行替代。
- [系统改名产生多个同名／历史相册] → 按用户指定规则保留旧相册，以 ID 和导入代次区分；不自动合并或清理用户的旧分类。
- [系统删除导致先收到成员清空] → 优先确认来源可用性与删除事件，在同一批核对中先处理来源生命周期，再合并仍有效来源的成员变化。
- [本地成员覆盖丢失] → 与来源快照分开持久化，事件重放与重启测试验证；不拿来源全量覆盖有效成员。
- [视频体积和分块数扩大] → 有界资源读取、可取消工作、进度按真实结果累积；分块目标不等于仓库无限容量。
- [锁屏只遮住界面却继续出声] → 播放会话统一失效与停止，再替换路由；用播放器替身和真实播放各验证一次。
- [多选保留了已隐藏的项目] → 共享查询、选择清理与执行前再校验，批量删除只使用仍有效的选择。
- [真实媒体进入演示逻辑] → 正式运行中移除演示执行与回退路径；缺能力准确禁用，不制造完成结果。
- [候选设计被当成批准] → TD 决策单独登记用户批准与验证，任务依赖该记录；文档齐全不代表选型已定。
- [仅写出密文被误当安全完成] → 验证算法实现、密钥／nonce 生命周期、认证与恢复，并检查敏感旁路；不是只看文件扩展名或搜索不到明文。

3. 后续实现先读取现状，不迁移虚构账号／密码／副本标志为真实数据；任何真实目录或用户原媒体不得被演示重置清除。

5. 真实来源、媒体及相册就绪后完成文件导出、三种删除和跨设备异常恢复；所有数据操作采用明确隔离副本验收。

7. 本轮不合并主规格、不归档旧变更、不提交或推送；完整实现并验收后再按用户要求处理归档。
